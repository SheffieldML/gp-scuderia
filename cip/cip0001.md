# CIP-0001: Interchange 0.1 capability coverage and schema evolution

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted - Approved 2026-11-26
- [ ] In Progress
- [ ] Implemented
- [ ] Closed

## Summary

GPc CIP-0016 delivers the GPc side of the interchange format. gp-scuderia owns the format itself, so the capabilities the format cannot yet express, and the adapters that cannot yet realise it, belong in a gp-scuderia plan. This CIP lists those gaps, orders them, and fixes the rule for adding a feature to the schema.

## Motivation

Phase A of CIP-0016 closed with three adapters (GPc in Python and C++, GPmat) matching GPy on two goldens. That covers exact GPs and sparse regression with rbf (including ARD), matern32, white, bias and sums. The refusals found along the way are the real scope of the work that remains:

- **Schema gaps.** The wire format is zero-mean and unscaled, so a `gp learn` model with default centring cannot be exported. There is no product kernel, Matérn 5/2, coregionalisation, non-Gaussian likelihood or multi-output model. PITC has no wire form.
- **Adapter gaps.** GPy has no `to_wire` yet, so nothing has been exported from the reference implementation. The GPyTorch, GPflow and GPJax entries in `registry/types.yaml` are `verified: false`. C++ reads JSON only; YAML is converted at the boundary.
- **Semantic mismatch.** GPc's CIP-0027 makes a trainable White own the Gram noise, and its `.model` stream does not record the opt-in that gives the wire semantics (K + white + sigma^2 I). Exact plus White models therefore cannot go through a `.model` file.
- **Infrastructure.** gp-scuderia is not yet published, has no CI, and `conformance.sh` depends on local paths.

Without a plan in this repository, each toolbox CIP decides these separately and the format drifts.

## Detailed Description

### Rule for extending the schema

A feature enters the schema only with (a) a golden in `examples/` carrying an `x-reference` generated by an independent implementation, (b) a negative fixture, and (c) a registry entry per framework that says supported, unsupported or not yet checked. A framework that cannot realise a feature raises. Features are additive within 0.1; renames and removals bump `schema_version`.

### Capability backlog, in order

1. **GPy `to_wire` and `from_wire`.** GPy is the oracle, so it must also write the format. Round-trip every golden.
2. **`kern.matern52` and `kern.prod`.** Both are supported by GPy and GPmat; GPc needs a product-kernel path in `CInterchange` (it has a tensor kernel).
3. **Mean and scaling.** *Decided 2026-11-26: carry both as optional fields.* A missing field means zero mean and no scaling, so every existing document keeps its meaning.
   - `mean`: `{type: mean.constant, value: c}` (further mean types later), so that the prior mean is `c` on the original target scale.
   - `normalizer`: `{type: normalizer.standardize, mean: m, std: s}` (or `normalizer.center` with `mean` only). It states that the model was fitted to `(y - m) / s`. Adapters report log likelihood and predictions on the original scale, with the Jacobian term `-n log s` included in the log likelihood, so goldens stay comparable across toolboxes.
   - An adapter that cannot realise a field raises. The `x-reference` of each new golden is generated by GPy, using its normalizer where `normalizer` is set.
   - Consequence for GPc: `CInterchange` maps `normalizer.center` onto the bias that `gp learn` already stores, which lets the export refusal for centred models go away. Scaling needs a check against GPc's scale handling before it is claimed.
4. **Noise semantics in `.model`.** Raise with GPc whether the stream should record the allow-white opt-in (a GPc CIP-0027 amendment), so exact plus White round trips.
5. **Coregionalisation and multi-output** (`kern.coregionalize`, `output_dim > 1`), matching GPc CIP-0038.
6. **Non-Gaussian likelihoods** (probit, Student-t) with an inference tag (`laplace`, `ep`).
7. **PITC and other approximation tags**, kept in the registry as unsupported until a second implementation exists.
8. **GPyTorch, GPflow, GPJax adapters**, each verified against the goldens before `verified: true`. *Done 2026-11-26 for Gaussian models.*
9. **YAML in C++** behind an optional yaml-cpp flag; until then convert at the boundary.
10. **Variational inference** (`inference: vi`, `variational` block) with a first golden from GPflow VGP or SVGP. See the design above.
11. **MCMC** (`inference: mcmc`, `prior`, `mcmc` block) with a golden verified statistically.

### Variational and MCMC approximations (design, reserved)

Added 2026-11-26. This section fixes how the format will store approximations that GPflow, GPJax and GPyTorch implement natively and that GPc, GPy and GPmat may refuse. Nothing here enters the schema until it meets the extension rule above; the tags are reserved in `registry/types.yaml` (`reserved_inference`) so no adapter invents its own spelling.

**Two axes, kept separate.** `approximation` says how the *covariance* is approximated (`ftc`, `dtc`, `dtcvar`, `fitc`, `pitc`). `inference` says how the *posterior over latent values* is approximated for a given likelihood (`laplace` today; reserved: `ep`, `vi`, `mcmc`). A sparse variational GP such as GPflow's SVGP uses both: `approximation: dtcvar`-style inducing inputs plus `inference: vi`. The collapsed bound (GPflow SGPR, GPJax `collapsed_elbo`) is already `dtcvar` with a Gaussian likelihood, so it needs no new tag.

**What the approximations are in each framework** (class names as found on 2026-11-26; check against each adapter when it is written):

| Approximation | GPflow | GPJax | GPyTorch | Stored state |
|---|---|---|---|---|
| Full-batch variational, q(f) over all n points | `VGP` | `variational_family` over the training inputs (`VariationalGaussian`) | `VariationalGP` with `VariationalStrategy` and inducing points equal to the data | mean and Cholesky factor of q(f) |
| Sparse variational, q(u) over m inducing values | `SVGP` | `VariationalGaussian` with `inducing_inputs`; `NaturalVariationalGaussian`, `ExpectationVariationalGaussian` are reparameterisations | `ApproximateGP` with `VariationalStrategy` and `CholeskyVariationalDistribution` | inducing inputs Z, mean and Cholesky factor of q(u), whitening flag |
| Collapsed sparse (Gaussian likelihood only) | `SGPR` | `CollapsedVariationalGaussian` | `InducingPointKernel` | none beyond `dtcvar` (q(u) is a function of the hyperparameters) |
| MCMC over hyperparameters or latent values | `gpflow.models.GPMC`, `SGPMC`, with priors on parameters, sampled by `tfp` HMC | `numpyro` or `blackjax` over a `Posterior` with priors | external (Pyro, `gpytorch` with priors) | prior on each parameter, plus draws |

GPy has `GPy.core.SVGP` and an HMC sampler over hyperparameter priors, so it is a candidate to support these later; GPc has Laplace, EP and IVM but no variational or sampling path; GPmat has neither for GP regression. Until a second implementation exists, adapters for GPc, GPy and GPmat raise `UnsupportedByFramework` naming the tag (`inference: vi`). The document is still schema-valid: refusal is a property of the adapter, not of the format.

**Rule: store only what cannot be recomputed.** Hyperparameters and data define the model. For Gaussian likelihoods and for Laplace, the posterior is a deterministic function of them, so the document stores no posterior. For `vi` the posterior is the optimiser's output and is not a function of the hyperparameters, so it must be stored. For `mcmc` the draws are the posterior. This keeps existing documents unchanged and gives one test for any future tag: can a second implementation recompute it?

**Proposed fields** (all optional, all rejected by validators that do not know them):

```yaml
likelihood: {type: likelihoods.bernoulli, link: probit}
inference: vi                      # reserved: vi | mcmc | ep
variational:                       # required when inference is vi
  family: variational.gaussian     # full-covariance Gaussian; mean_field and natural are later tags
  whiten: true                     # q(u) is over L^{-1} u when true, as in GPflow and GPyTorch
  inducing_inputs: [[...], ...]    # Z; omit for full-batch VGP (Z = X)
  q_mean:  [...]                   # m values (or n for VGP), per output column
  q_chol:  [[...], ...]            # lower-triangular factor of the covariance, row-major
mcmc:                              # required when inference is mcmc
  sampler: hmc                     # provenance only: hmc | nuts | slice
  target: [kernel.variance, kernel.lengthscale]   # parameter paths that were sampled
  draws: {chains: 4, per_chain: 500, thinning: 1}
  samples: {kernel.variance: [...], kernel.lengthscale: [...]}  # flat list, chain-major
prior:                             # on any numeric parameter, used by mcmc and by MAP fits
  kernel.lengthscale: {type: prior.gamma, shape: 2.0, rate: 1.0}
```

Conventions: `q_chol` follows GPflow's `q_sqrt` (lower triangular, the covariance is `L L^T`); GPJax and GPyTorch adapters convert on the way in and out. Whitening is stored because the same numbers mean different posteriors with and without it. Optimiser state, minibatch size, learning rate and the training trace are provenance and live under `x-` fields, never in the semantics. Priors are stored on the constrained scale the model reports; bijectors are an adapter detail.

**Verification, because these are not exactly reproducible.**
- `vi` goldens carry `elbo` in `x-reference`, along with predictive `mean` and `var`, evaluated at the stored q. An adapter reproduces them without optimising, so the check is deterministic and tight. A second golden with a Gaussian likelihood and `Z = X` states the known optimum: the optimal SVGP bound equals the collapsed bound, which cross-checks the VI and `dtcvar` code paths against each other.
- `mcmc` goldens cannot be matched draw by draw. They carry posterior mean and variance of each sampled parameter with Monte Carlo standard error, generated by an independent chain; the tolerance is a multiple of that error and the adapter test reports effective sample size alongside.
- Non-Gaussian `vi` needs a quadrature rule for the expected log likelihood. The golden records which one (`x-quadrature: gauss-hermite-20`) because the ELBO value depends on it.

**What stays out of 0.1.** Student-t and EP (candidates listed in the Laplace task), structured or Kronecker variational families, deep or multi-layer models, and stochastic-process priors on inducing locations. Each needs its own entry when a second implementation exists.

### Infrastructure

Publish the repository, add CI that runs `scripts/conformance.sh` with tool locations from the environment (removing the home-directory defaults), and run GPy's conformance in a pinned environment so the oracle does not move silently.

## Implementation Plan

1. Review this CIP and agree the order (the item 3 decision is made).
2. Accepted 2026-11-26; created backlog tasks for items 1 to 9 and the infrastructure.
3. Each item lands with its golden, negative fixture and registry update, and a conformance run across all adapters.

## Backward Compatibility

All items are additive to 0.1. Item 3 keeps the zero-mean rule as the default for documents without the new fields, and `docs/overview.md` is updated to say so when it lands.

## Testing Strategy

`scripts/conformance.sh` against GPy-generated `x-reference` blocks, negative fixtures in `tests/invalid/`, and per-adapter unit tests in each toolbox repository.
