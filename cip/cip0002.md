# CIP-0002: GPML as a conformance target

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted - Approved 2026-11-27
- [ ] In Progress
- [ ] Implemented
- [ ] Closed

## Summary

Add the GPML MATLAB/Octave toolbox (Rasmussen and Nickisch, the code that accompanies the Rasmussen and Williams book) as a sixth implementation in the comparison. GPML is the most widely cited reference implementation of the models in the book, and it carries its own Laplace and EP code, so it gives the Laplace goldens a second independent check beyond GPy and our numpy implementation. The work is an adapter that maps the wire format onto GPML's `meanfunc`, `covfunc`, `likfunc` and `inffunc` arguments, a registry entry, and a CI job that runs it live under Octave and reports through the existing report.

## Motivation

- **Independence.** The goldens' `x-reference` comes from GPy. For exact regression, GPy, GPflow, GPyTorch and GPJax share much of their lineage and conventions. GPML shares none of that code, so agreement is stronger evidence that the wire semantics are right and not just GPy's habits.
- **Laplace and EP.** `infLaplace` is the Laplace approximation of the book, and `infEP` is the reference EP. GPmat refuses non-Gaussian models, and GPflow, GPyTorch and GPJax refuse the Laplace goldens, so only GPy, GPc and our numpy check currently cover them. GPML would be the first outside implementation to confirm them. `infEP` also gives us a reference for the reserved `ep` inference value.
- **Sparse reference.** GPML implements FITC (`infFITC`, `covFITC`) from the same lineage as the book, which is an independent check on the `fitc` goldens.
- **Reach.** GPML users in MATLAB and Octave could exchange models with the rest of the ecosystem through the same files.

## Detailed Description

### Name

GPML is distinct from GPmat (Lawrence's MATLAB toolbox, already in the registry as `gpmat`). The registry key for the new target is `gpml`.

### Expected coverage

This table is the design hypothesis. Phase 1 below confirms or corrects each row against the actual toolbox before any claim goes into the registry.

| Golden | GPML construction | Expected |
|---|---|---|
| ftc_rbf_white | `covSEiso` plus `covNoise` or `likGauss` | match |
| ftc_prod_matern52 | `covProd` of `covMaterniso` (d=5) and `covSEiso` | match |
| ftc_standardize | centre and scale outside GPML, as the wire `normalizer` says | match |
| dtcvar_mean_constant | `meanConst`, with FTC maths | match |
| dtcvar_ard_data | `covSEard` | refuse unless a VarDTC route exists; GPML has FITC but no DTCVAR |
| fitc_matern52 | `covFITC` with `infFITC` | match, if inducing inputs and Gram noise conventions line up |
| ftc_icm, ftc_lcm | none | refuse (no coregionalisation) |
| laplace_bernoulli | `likErf` with `infLaplace` | match |
| laplace_poisson | `likPoisson` with `infLaplace` | match |

GPML hyperparameters are logs of the natural parameters, and `covMaterniso` takes its smoothness as `d = 2*nu`. The adapter handles both. As elsewhere, anything GPML cannot realise raises `UnsupportedByFramework` rather than substituting.

### Adapter

An Octave package under `octave/gpml/` (separate from `octave/gpscuderia/`, which serves GPmat) with `gpmlRead`, `gpmlToModel` and `gpmlReference`. It mirrors the existing GPmat adapter's interface so `compare.py` can treat it uniformly. `compare.py` gains a `gpml` mode that shells out to `octave-cli`, writes the result to a JSON file in the same shape as the Python frameworks, and returns that file's contents. GPML is not a Python package, so the same shell-out route would serve GPmat, which still runs through `conformance_gpmat.m`. Moving GPmat onto it is a separate, optional step.

### Obtaining GPML

The toolbox ships as a zip at gaussianprocess.org/gpml. CI downloads a pinned release (v4.2 at the time of writing), verifies a checksum recorded in `ci/`, and unpacks it. The checksum guards against the archive changing under us. No GPML code is vendored into this repository, since the toolbox is distributed under its own licence.

### CI

A `gpml` job installs `octave-cli` from apt, fetches and checks GPML, runs `compare.py gpml`, and uploads the JSON like the other frameworks. The report picks it up as another column. The job is `continue-on-error` until it has run green once on GitHub, after which it joins the required set. The existing `frameworks-latest` canary does not apply, since GPML releases are rare; the pinned archive is the only mode.

### What this does not cover

GPML's variational and MCMC options (`infVB`, `infMCMC`) map onto the reserved `vi` and `mcmc` values from CIP-0001, and are out of scope here. GPML models cannot be exported to the wire format by this CIP, only compared against it. An export path is a later plan if wanted.

## Implementation Plan

1. **Probe.** Download GPML into a scratch directory, and for each row of the table above, write a short Octave script that builds the model by hand and compares it with the golden's `x-reference`. Record which rows match, which differ and why. Correct the table.
2. **Adapter.** Write `gpmlRead`, `gpmlToModel`, `gpmlReference`, with refusals that match the probe.
3. **Comparator.** Add a `gpml` path to `scripts/compare.py` using `octave-cli`, and fill `framework_verification.gpml` in `registry/types.yaml` from the probe.
4. **CI.** Add the `gpml` job, the pinned archive checksum, and the report column.
5. **Optional.** Move the GPmat check onto the same shell-out route so both MATLAB-family tools appear in the report identically.

## Backward Compatibility

Additive. No schema change and no change to existing adapters. If the probe shows that a golden's wire semantics differ from GPML's in a way the adapter cannot bridge, that is a finding to record in the registry (a refusal with a reason), not a reason to change the golden.

## Testing Strategy

The comparison is the test. Success means every golden has an expected status for `gpml` (match or refused with a reason), the Octave results land in the report, and an unexpected status fails the job as it does for the other frameworks. The Laplace rows are the most valuable outcome: agreement within tolerance would be the first external confirmation of those goldens.

## Open Questions

- Does Octave run GPML v4.2 cleanly on the apt version of Octave in `ubuntu-latest`, or does the job need a pinned Octave? The probe answers this.
- Does GPML's FITC treat the Gram noise as `sigma^2` on the diagonal in the way the wire's `fitc` does? The probe answers this too.
- Should the pinned GPML archive be mirrored somewhere we control, in case the download location moves?

## Related Requirements

None yet. CIP-0001 covers the format and its verification rule; this plan extends the set of implementations that verification uses.
