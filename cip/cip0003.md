# CIP-0003: Declarative framework files and benchmarks driving the comparison

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted
- [x] In Progress
- [ ] Implemented
- [ ] Closed

## Summary

Describe each framework in its own YAML file (`frameworks/<name>.yaml`): how to install it, how to run it, and which parts of the wire format it supports. Let those files, together with the goldens, drive the comparison and generate the CI matrix. Define one process-level runner contract (JSON in, JSON out) that Python, Octave and command-line frameworks all satisfy. Then add benchmark files (`benchmarks/<name>.yaml`) for numerical and timing comparisons, run automatically against every framework that declares the capabilities a benchmark requires.

## Motivation

Adding a framework today means editing five places:

- the `PACKAGES` dict and `OCTAVE_RUNNERS` in `scripts/compare.py`;
- the `framework_verification` block in `registry/types.yaml`;
- `ci/pinned-*.txt` and `ci/latest-*.txt`;
- the job matrix in `.github/workflows/conformance.yml`;
- the loops in `scripts/conformance.sh`.

CIP-0002 made this concrete: GPML and GPmat took a bespoke Octave runner and a bespoke CI job each. The `framework_verification` lists are the worst of these, because they are hand-maintained predictions of which goldens each framework will refuse. They can drift from the truth without anything noticing, and a new golden requires touching every framework's list.

The comparison is also limited to correctness at a few points. Users choosing between frameworks also ask how they scale and how they behave when conditioning is poor. We want to answer those from the same wire models, with no per-framework scripts.

This aligns with the project tenets on interoperability (speak formats the community already uses; a new framework should not need changes to the harness) and on asserting and verifying (declared capabilities are checked against behaviour in both directions).

## Detailed Description

### Framework files

`frameworks/<name>.yaml` holds everything that is specific to one framework:

```yaml
name: gpflow
runners:
  - id: python
    kind: python                      # python | octave | command
    entry: gp_scuderia.gpflow_adapter:reference
    install:
      pinned: ci/pinned-gpflow.txt
      latest: ci/latest-gpflow.txt
    versions: [gpflow, tensorflow, numpy]
capabilities:
  approximations: [ftc, dtcvar, fitc]
  kernels: [rbf, matern32, matern52, bias, white, add, prod]
  likelihoods: [gaussian]
  inference: [exact]
  extras: [mean.constant, normalizer.standardize]
```

- A framework may have several runners. GPc has three (C++ tests, command line, Python), and each reports separately.
- `kind: octave` frameworks (GPML, GPmat) add `fetch:` (URL plus sha256, or git URL plus revision) and `apt: [octave]`. The existing checksum file `ci/gpml.txt` becomes part of this.
- Capability names use the vocabulary already in `registry/types.yaml`, so a new kernel, likelihood or inference method is added in one place and every framework file can then claim it. The reserved values `ep`, `vi` and `mcmc` fit as extra `inference` entries.

### Capability granularity

Capabilities start coarse, at the type level, but the schema allows refinement where it matters. Each entry in a capability list is either a bare name or a name with options:

```yaml
kernels:
  - rbf                              # coarse: all rbf goldens
  - matern52: {options: [ard]}       # refined: ARD supported
  - prod: {options: [same_active_dims]}
```

A bare name claims every option. A name with `options` claims only those, and a golden's features are extended with the options it exercises (for example `ard`, `active_dims`). Matching is by feature set containment, so goldens that exercise no options need no change. Refinement is added one family at a time, only when a framework's refusal pattern requires it, and the registry vocabulary lists the options each type recognises. Unknown options in a framework file fail validation.

### Expectations are derived

The harness reads each golden's features (approximation, kernel types, likelihood, inference, mean, normalizer, output dimension) and compares them with the framework's declared capabilities:

- all features declared: the runner must match within the golden's tolerance;
- any feature missing: the runner must refuse, with a reason.

A declaration that disagrees with behaviour fails in both directions: a framework that matches something it said it could not do (the declaration is stale), or one that refuses something it claimed. The `framework_verification` block is removed from the registry.

### Runner contract

All runners satisfy one contract, so the harness never imports framework code itself:

1. The harness writes a task file: a list of tasks, each a wire model, an operation (`log_likelihood`, `predict`, `gradient`, ...), query points, and any timing options.
2. The runner executes the tasks and writes a result file. Each result is `{log_likelihood, mean, var, ...}`, `{refused: reason}` or `{error: message}`, plus `seconds` when timing is requested.
3. For `kind: python`, a generic wrapper (`python -m gp_scuderia.run --entry module:function`) imports the entry point named in the YAML and calls it, turning `UnsupportedByFramework` into `refused`. The existing adapters' `reference(doc, Xnew)` is the entry point unchanged.
4. For `kind: octave`, the command is a `run*.m` script that reads and writes the same JSON; `octave/gpml/runGpml.m` and `octave/gpmat/runGpmat.m` already do this for the goldens.
5. For `kind: command`, any executable that speaks the same JSON.

Each runner executes in its own environment (a venv, Octave, or the GPc build), which keeps framework dependencies from conflicting with each other or with the harness. An external framework can be tested by naming an installed package in `entry:`, so adapters do not have to live in this repository.

### Generated CI

A first job reads `frameworks/*.yaml` and emits the job matrix as JSON for `fromJSON`. A new framework then needs a YAML file and, for Python, an adapter module. Pinned and latest modes, version recording, the report columns and the weekly canary come from the same files.

### Benchmarks

`benchmarks/<name>.yaml` describes a task generator plus metrics:

```yaml
name: scaling_exact_rbf
kind: timing                          # accuracy | timing | gradient
requires: {approximations: [ftc], kernels: [rbf], likelihoods: [gaussian]}
sizes: [100, 500, 2000]
seed: 0
operations: [log_likelihood, predict]
repeats: 5
warmup: 1
metrics: [seconds_median, seconds_iqr]
```

- Datasets are generated from the seed and written as wire models, so every framework receives identical inputs.
- `requires` uses the capability vocabulary. A framework lacking a required capability is skipped for that benchmark, and this is reported as skipped, not as a failure.
- **Accuracy benchmarks** compare each framework with the oracle (or with each other where no oracle scales): gradient agreement, ill-conditioned kernels, very long or short lengthscales, large-n log-likelihood, and the ordering of sparse bounds. These may fail the build.
- **Timing benchmarks** are measured inside the runner after warmup, so imports, JIT compilation and Octave start-up are excluded. CI runners are shared and noisy, so timings are reported with the hardware recorded, never gate the build, and are best read as ratios. A dated history (an artifact per run) would make trends visible and is deferred.

### Out of scope

- Optimisation and training comparisons (hyperparameter fitting differs across frameworks; we compare evaluation at fixed parameters, as now).
- Variational and MCMC inference, which remain tracked by `2026-11-26_variational-and-mcmc`.
- Hosting benchmark history anywhere beyond CI artifacts.

## Implementation Plan

1. **Framework files, no behaviour change.** Write `frameworks/*.yaml` for gpy, gpflow, gpytorch, gpjax, gpc, gpml and gpmat; add the capability schema; derive golden features. `compare.py` reads these files in place of `PACKAGES`, `OCTAVE_RUNNERS` and `framework_verification`. Remove the registry block. Generate the CI matrix from the files.
2. **Runner contract.** Add the task and result schemas and `gp_scuderia.run`. Move the Python adapters behind it and move the Octave scripts onto the same task file. `compare.py` becomes a client of the contract.
3. **Accuracy benchmarks.** Add the generator, the first benchmark files (gradient agreement, conditioning, lengthscale extremes) and report sections.
4. **Timing benchmarks.** Add in-runner timing, the scaling benchmark, hardware recording and the report table. If CIP-0005 is accepted, it defines the benchmark files measured here (exact, sparse and Laplace timing, tiers, cold time, thread rule) and this step delivers them; the machinery stays here.
5. **Documentation.** A short "add a framework" page, written after the design is validated by adding one new framework through it.

## Backward Compatibility

The goldens, wire format and adapters are unchanged. `scripts/conformance.sh` and the existing report keep working through step 1. The `framework_verification` block disappears from the registry, so anything reading it must move to the framework files (nothing outside this repository is known to).

## Testing Strategy

- After step 1 the report must be identical to today's, cell for cell, as a regression check on the refactor.
- A deliberately wrong declaration (claiming a capability a framework lacks, and the reverse) must fail the build in each direction.
- Step 5 is itself a test: add a framework we do not yet support (for example a second GPJax route or GPyTorch variational) using only a YAML file and an adapter.
- Timing benchmarks are checked for repeatability by running twice and comparing medians; no timing threshold is asserted.

## Open Questions

- ~~How fine-grained should `capabilities` be?~~ Decided 2026-11-27: flexible. See "Capability granularity" below.
- Should runners batch all tasks in one process (fast, but one crash loses everything) or isolate per task? Batch with per-task catch, with a retry in isolation on crash, is the likely answer.
- Where do timing histories live, if we keep them? The repository, an artifact store, or a separate results branch.
- Should a framework YAML be allowed to override tolerances for a specific golden (for example the FITC convention), or must differences go through the registry?
