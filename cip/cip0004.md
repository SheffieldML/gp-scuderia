# CIP-0004: Standardised evaluation and a learned guide to choosing a GP package

## Status

- [x] Proposed - Initial idea documented
- [ ] Accepted
- [ ] In Progress
- [ ] Implemented
- [ ] Closed

## Summary

Use the machinery gp-scuderia already has (a common wire format, declared framework capabilities checked against behaviour, a single runner contract, seeded benchmarks) to answer the question a user actually asks: *which GP package, and which algorithm in it, should I use for my problem?*

The plan has three layers:

1. **Standardised tests.** A fixed set of basic algorithm families, a task suite, one training and evaluation protocol, and one set of metrics, applied to every framework that declares the capabilities a test needs.
2. **A results matrix.** Rows are configurations (framework × algorithm × settings), columns are tasks, and entries are test metrics and costs, stored as a durable, versioned table.
3. **A learned guide.** A probabilistic matrix factorisation of that matrix, after Fusi, Sheth and Elibol (2018), which predicts how untried configurations will do on a new dataset from a few that have been run on it, and proposes what to try next with cost taken into account.

This is an umbrella CIP. It fixes the direction, the algorithm families, the protocol and the order of work. Each layer is delivered by a sub-CIP (listed below), and CIP-0005, the first benchmarks, is proposed alongside it.

## Motivation

- **Users choose packages on anecdote.** GPy, GPc, GPmat, GPML, GPflow, GPyTorch and GPJax differ in approximations, inference methods, numerical robustness and speed, but there is no common, reproducible comparison. Papers that compare them usually do so on one problem, with one package's defaults.
- **gp-scuderia can measure what others cannot.** Because models cross frameworks through the wire format, a model fitted in any framework can be exported and re-evaluated by an independent implementation. That separates *evaluation correctness* (does the framework compute the objective and predictions correctly? already covered by conformance) from *fit quality* (did its training find a good model?). We know of no published GP comparison that separates the two, but we have not surveyed the literature for this CIP.
- **The pieces are in place.** CIP-0003 gave framework files with checked capabilities, a process-level runner contract, a generated CI matrix and accuracy benchmarks that skip frameworks lacking a capability. The missing parts are training, timing, tasks beyond synthetic ones, a results store, and the guide itself.
- **A recommender needs a matrix.** "Which algorithm on which data" is a collaborative-filtering problem: few configurations are run on any one dataset, but structure is shared across datasets. Fusi et al. showed that a GP-LVM over a pipelines × datasets matrix of held-out performance, combined with expected improvement, picks good AutoML pipelines for new datasets, and reported better results than auto-sklearn and random search on their benchmark. Our matrix is far smaller and more structured, so whether the approach transfers is itself a question the pilot matrix has to answer. If it does, the guide would be a GP-LVM fitted in GPy or GPc.

## Detailed Description

### Structure of the matrix, and what it means for the design

Conformance checks that, at fixed parameters, the same algorithm gives the same answer in the frameworks that support it, to stated tolerances. The accuracy benchmarks show this is not universal: at noise 1e-4 five frameworks agree with each other and differ from the GPy reference by about 0.4 in log likelihood, and DTCVar at n = 1000 differs by about 1e-2 in three of them (both recorded as known mismatches in `benchmarks/*.yaml`, causes undiagnosed). We expect that, after training, differences between frameworks for one algorithm come mainly from optimisers, initialisation, jitter and defaults, but this is a hypothesis to test, not a premise. If it holds:

- Rows for the same algorithm in different frameworks should be close to collinear in accuracy, so the accuracy matrix would be low rank largely along the **algorithm and settings** axis, which is where factorisation helps most. The pilot matrix tests this directly: if same-algorithm rows are not close, framework becomes a first-class axis and the guide must model it.
- Framework differences show mainly in **cost** (time, memory, compilation), **robustness** (failures, NaNs, sensitivity to seeds) and **features** (capabilities). These are answered directly from capability files, conformance, timing and failure rates, and enter the guide as separate objectives and constraints, not as entries to impute.
- **Refusals are structurally missing**, not missing at random. A configuration a framework cannot express is filtered out by capability before factorisation and is never imputed. Failures and timeouts on capable configurations are informative and are recorded as outcomes (censored for timeouts), not dropped.

### Basic algorithm families

Chosen to span the decisions a user faces. Each family should run in at least two frameworks, so that framework and algorithm effects can be separated.

| # | Family | Settings varied | Frameworks (expected) | Wire work |
|---|---|---|---|---|
| A1 | Exact GP regression, type-II maximum likelihood | kernel (rbf, matern32, matern52), ARD on/off, restarts | all seven | none |
| A2 | Collapsed sparse regression: DTCVar (SGPR), FITC | M ∈ {16, 64, 256}; inducing inputs fixed (k-means) or optimised | GPy, GPc, GPmat, GPflow, GPJax; FITC also GPML | flag for learnable inducing inputs |
| A3 | Stochastic variational GP (SVGP) | M, minibatch size, whitened or not, natural gradients or Adam | GPflow, GPyTorch, GPJax, GPy | q(u) on the wire with a whitening convention |
| A4 | Non-Gaussian likelihoods: Laplace, EP, VI | Bernoulli, Poisson | GPy, GPML (Laplace, EP); GPflow, GPyTorch, GPJax (VI) | `ep` and `vi` inference tags, goldens |
| A5 | Multi-output: ICM and LCM | rank, number of terms | GPy, GPc; GPflow, GPyTorch with new adapters | already on the wire |
| A6 | Exact GP by iterative solvers (conjugate gradients, BBMM) | preconditioner rank, tolerance | GPyTorch | inference-route tag |
| R | Reference rows | constant-mean predictor; Bayesian linear regression (GP with `kern.linear`) | GPy (or numpy) | none |

A1 and A2 are the first wave: together they already answer "how much accuracy does a sparse method cost me, and how much time does it save, in each package?". Later candidates, not in scope here: MCMC over hyperparameters (GPflow, GPJax with BlackJAX), structured kernel interpolation (KISS-GP) for low-dimensional inputs.

### Standardised measurements

For every (configuration, task, split):

- **Accuracy:** test negative log predictive density (NLPD, the primary metric, because it rewards calibrated uncertainty), RMSE, and 95% interval coverage. For classification, NLPD (log loss), error rate and expected calibration error.
- **Cost:** training time, prediction time, first-call (cold) time separately from warm time (JIT and graph compilation are a real cost to users, so they are reported, not hidden), and peak memory where the runner can measure it.
- **Robustness:** status (`ok`, `refused`, `error`, `nan`, `timeout`) and the spread of the metric across seeds.
- **Audit:** the fitted model is exported as a wire file and re-evaluated by the oracle. Disagreement between the framework's reported metric and the oracle's is reported as an evaluation fault, separately from fit quality.

### Standardised protocol

- **Precision and hardware.** float64 throughout (JAX x64 enabled, torch double), CPU only to begin with, thread counts fixed and recorded per run, hardware recorded.
- **Splits.** Fixed, seeded train/test splits per task (10 for small tasks, fewer for large), shipped with the task.
- **Normalisation.** By the wire `normalizer`, so every framework sees the same scaling.
- **Initialisation.** One shared initial wire model per (task, configuration family, seed), so differing defaults for initial values do not masquerade as framework differences. A second "framework defaults" arm may be added later, because users do meet the defaults.
- **Budget.** A fixed number of optimiser iterations or seconds, whichever is reached first, with the optimiser recorded.
- **Fairness.** Two of the seven frameworks (GPy, GPc) and GPmat are maintained by the same group that runs this comparison. Adapters, settings and budgets for each framework are open to review by that framework's maintainers, and results are published with the adapter versions that produced them.

### Task suite

- **Synthetic families** from the seeded generator, varying n, d, noise, lengthscale relative to input spacing, smoothness (data drawn from Matérn or RBF processes, or from non-GP functions), non-stationarity and conditioning.
- **Real regression:** standard small UCI sets (for example yacht, concrete, energy, kin8nm, power, protein, naval).
- **Classification:** a small subset of OpenML-CC18.
- **Counts:** a few count datasets.
- Each task carries **descriptors** computed the same way everywhere: n, d, a signal-to-noise estimate, lengthscale over median nearest-neighbour spacing from a quick reference fit, and a condition number estimate. These are the meta-features the guide uses for a new dataset.

Synthetic tasks are cheap, but tasks drawn from a GP prior favour the matching kernel. The suite must not be dominated by them.

### The guide

- Fit a GP-LVM (or PMF with a linear kernel, as the baseline) to the configurations × tasks NLPD matrix, and a second model to log training time.
- For a new dataset: compute its descriptors, run a small warm-start set of configurations, predict the rest with uncertainty, and propose the next configuration by expected improvement per unit cost (or over the accuracy and time Pareto front). Fusi et al. left cost and dataset meta-features to future work; we need both from the start.
- Evaluate by leaving tasks out, measuring regret against the best configuration in hindsight, with three baselines: the best configuration on average, random choice among capable configurations, and the nearest neighbour task by descriptors.
- Ship as a command, for example `gp-scuderia suggest data.csv --budget 60s`, that only proposes configurations whose framework declares the needed capabilities.

### Sub-CIPs

Numbers are not reserved. Each sub-CIP takes the next free number when it is proposed (0006 is already taken by an unrelated CIP), and this table is updated then. Provisional names are used below.

| Provisional name | Title | Delivers | Depends on |
|---|---|---|---|
| CIP-0005 | First benchmark suite | fixed-parameter timing (exact, sparse, Laplace), gradient agreement, sparse bound properties, task descriptors, the benchmark selection rule | CIP-0003 machinery |
| training | Training protocol | `fit` operation in the runner contract, shared initialisation, budgets, export and oracle audit, `x-training` block | CIP-0005 (gradients) |
| tasks | Task suite | `tasks/` directory: synthetic families, real datasets fetched with checksums, fixed splits, descriptors, licensing record | none |
| vi-ep | Variational and EP inference on the wire | SVGP q(u) and its whitening convention, `vi` and `ep` tags, iterative-solver tag, goldens; absorbs backlog `variational-and-mcmc` | training, for trained benchmarks |
| store | Results store | long-table result schema, scheduled full runs, durable storage and publication; would answer CIP-0003's open question on timing histories | training, tasks |
| guide | The guide | GP-LVM over the results, cost-aware acquisition, descriptors, task-held-out evaluation, `suggest` command | store |

## Implementation Plan

1. **CIP-0005.** Benchmarks that run with the current contract plus a gradient operation. These give the first timing and robustness picture and fix the task descriptor code.
2. **Training and task suite in parallel.** Training protocol and task suite.
3. **Pilot matrix.** Families A1, A2 and R on the first tasks, every capable framework, run on a schedule. This is the first deliverable a user can read: an accuracy and time table per task family.
4. **Variational and EP inference.** Families A3, A4 and A6. The matrix gains the rows where GPflow, GPyTorch and GPJax are strongest.
5. **Results store.** Results store and published tables.
6. **The guide.** The guide, once the matrix has enough tasks (a working threshold: 50 or more) for held-out evaluation to mean something.

## Backward Compatibility

Additive. Goldens, the wire format at 0.1 and existing adapters are unchanged. Training adds an operation to the runner contract (the training CIP) and an experimental `x-training` block. Frameworks that do not implement `fit` are reported as skipped for trained benchmarks.

## Testing Strategy

- Each sub-CIP carries its own tests. The guide is tested against its baselines by task-held-out regret.
- The audit (oracle re-evaluation of exported fitted models) is itself a test of every adapter's export path.
- Repeatability: two runs of the pilot matrix should give the same ranks of configurations per task up to seed noise. Timing is compared by medians and never gates the build.

## Open Questions

- Should the protocol include a "framework defaults" arm alongside shared initialisation, since that is what users experience?
- How much compute can a scheduled run use, and should a GPU tier exist (GPyTorch and GPJax are designed for it)?
- Should non-GP baselines (for example gradient-boosted trees) appear as reference rows, so the guide can say when a GP is the wrong tool?
- How should timeouts enter the factorisation: as censored observations, or as a separate failure model?
- Where should results be published, and under what licence?
- How do framework maintainers review their adapters and settings: by invitation, or through an open process on this repository?
