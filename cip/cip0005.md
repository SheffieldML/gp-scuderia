# CIP-0005: First benchmark suite

## Status

- [x] Proposed - Initial idea documented
- [ ] Accepted
- [ ] In Progress
- [ ] Implemented
- [ ] Closed

## Summary

The first sub-CIP of CIP-0004. It chooses the benchmarks to build now, while the runner contract still evaluates models at fixed parameters, and states the rule for admitting a benchmark. It adds four things:

1. **Timing at fixed parameters** for exact regression, collapsed sparse regression and Laplace classification, across sizes. Ownership is split to avoid duplication. CIP-0003 step 4 (backlog task `timing-benchmarks`) is the single delivery vehicle: it builds the machinery (in-runner timing, repeats, hardware recording, the report table). This CIP defines what is measured: the three benchmark files, `pr` and `scheduled` tiers, cold time, and the thread rule. Those extend the machinery and are built under the same task.
2. **Gradient agreement**, the benchmark CIP-0003 deferred, via a small extension of the runner contract. Every trained benchmark later rests on gradients being right in wire units.
3. **Sparse approximation property checks** that need no oracle at large n.
4. **Task descriptors** recorded with every case, so that these benchmarks are the first columns of the CIP-0004 results matrix rather than a separate table.

It also adds two cases to the existing accuracy benchmarks.

## Motivation

CIP-0004 needs a training protocol and a task suite (sub-CIPs not yet proposed) before it can produce the matrix. Neither exists yet, but a good deal of what users ask can be answered now, at fixed parameters:

- *How fast is it?* Fixed-parameter log likelihood and prediction is the inner loop of every training run, so its cost and scaling should indicate much of a framework's training cost. That is a hypothesis: optimiser overhead, restarts and autodiff or compilation costs also matter, and the later trained benchmarks will show how well fixed-parameter timing predicts them.
- *Can I trust the gradients?* Every adapter converts between wire parameters and native ones (GPc `inverseWidth`, GPyTorch `outputscale`, GPflow softplus variables, GPML log hyperparameters, GPJax `obs_stddev`). A conversion that is right for values can still be wrong for derivatives, and that only shows when training starts.
- *Where do sparse methods break?* Known properties of the approximations can be checked at sizes where no exact oracle is practical.

Building these first also exercises the parts of the harness the later CIPs depend on: timing inside the runner, a contract with more than one operation, and descriptors.

## Detailed Description

### Rule for admitting a benchmark

A benchmark is added only if it meets all of these:

1. **It answers a question a user asks when choosing.** It must be possible to state the question in one line in the benchmark's `description`.
2. **It can discriminate.** It is expected to separate frameworks or algorithms on at least one case. A benchmark on which everything agrees by construction belongs in conformance, not here. (Accuracy benchmarks are the exception in one direction: agreement is the expected result, and the value is in finding the cases that disagree.)
3. **It runs through the contract.** No framework-specific script; frameworks without a required capability are skipped and reported as skipped.
4. **It has a cost tier.** `pr` cases run on every pull request and keep the whole suite within a few minutes per framework; `scheduled` cases run weekly and may take longer.
5. **It records descriptors** for every case (below).

### 1. Timing at fixed parameters

Three timing benchmarks, each measuring `log_likelihood` and `predict` separately. Timing uses the CIP-0003 rules: measured inside the runner, warm-up excluded, median and interquartile range of repeats, hardware recorded, never gating. In addition, the **first call** is timed and reported separately as cold time, because JIT compilation (JAX, TensorFlow graphs) and Octave function loading are real costs to users.

```yaml
name: timing_exact
kind: timing
description: How does exact GP evaluation scale with n in each framework?
requires: {approximations: [ftc], likelihoods: [gaussian], inference: [exact]}
seed: 10
base: {input_dim: 1, noise: 0.1, approximation: ftc,
       kernel: {type: kern.rbf, variance: 1.0, lengthscale: 1.0}}
grid:
  n: {pr: [250, 1000], scheduled: [250, 1000, 4000, 8000]}
  input_dim: [1, 8]
  kernel: [kern.rbf, kern.matern52]
n_predict: 1000
operations: [log_likelihood, predict]
repeats: 5
warmup: 1
metrics: [seconds_median, seconds_iqr, seconds_cold]
```

```yaml
name: timing_sparse
kind: timing
description: How do collapsed sparse methods scale with n and M?
requires: {likelihoods: [gaussian], inference: [exact]}   # approximation varies by case
grid:
  approximation: [dtcvar, fitc]
  n: {pr: [2000], scheduled: [2000, 10000, 50000]}
  inducing: {pr: [32, 128], scheduled: [32, 128, 512]}
  input_dim: [2]
```

```yaml
name: timing_laplace
kind: timing
description: What does Laplace classification cost, including the inner Newton iterations?
requires: {likelihoods: [bernoulli], inference: [laplace]}
grid:
  n: {pr: [200, 1000], scheduled: [200, 1000, 4000]}
  input_dim: [2]
```

Fairness rules for all timing:

- float64 in every framework (the adapters already do this; the runner asserts it and records the dtype).
- CPU only. Thread count fixed by environment (`OMP_NUM_THREADS`, `MKL_NUM_THREADS`, `OPENBLAS_NUM_THREADS`, and the TensorFlow, torch and XLA equivalents) and recorded. Each benchmark runs twice, at one thread and at all available threads, because frameworks may differ in parallel efficiency as well as in single-thread speed. Whether they do is something these runs will show.
- BLAS library and version recorded where the runner can find it.
- The report shows ratios to the fastest framework for each case, alongside absolute times.

Capability already decides the interesting skips. For example, GPyTorch declares no collapsed sparse approximation and GPflow and GPJax declare no FITC, so `timing_sparse` reports them as skipped. That is a finding for the user, not a gap in the benchmark.

### 2. Gradient agreement

**Contract extension.** The task file gains an optional `operations` list per task, defaulting to the current behaviour (`[log_likelihood, predict]`). A new operation, `gradient`, returns the derivative of the log likelihood with respect to every wire parameter, keyed by its path in the wire tree (for example `kernel.parts.0.lengthscale`, `likelihood.variance`), in wire units: natural, positive, untransformed values. A framework that cannot provide gradients refuses the operation, which is reported per operation. `schemas/task.schema.json` and `schemas/result.schema.json` move to `gp-scuderia-task/2` and a matching result version; version 1 files are still accepted.

**Reference.** The GPy oracle's analytic gradients, cross-checked against central finite differences of the oracle's own log likelihood, so the reference does not rest on GPy's gradient code alone.

**Benchmark.** Run on every existing golden and on the conditioning and lengthscale-extreme cases, so gradients are checked where values are already known to be hard. Tolerance is relative, `1e-5` by default, with an absolute floor for parameters whose gradient is near zero.

```yaml
name: gradient_agreement
kind: gradient
description: Are the gradients each framework would train with correct in wire units?
cases_from: [goldens, lengthscale_extremes, conditioning]
operations: [gradient]
reference: {oracle: GPy, check: central_difference, step: 1.0e-6}
tolerance: {relative: 1.0e-5, absolute: 1.0e-8}
```

Gradients with respect to inducing inputs are included where a framework exposes them, and reported separately, because the training protocol is expected to make optimising inducing inputs a setting.

### 3. Sparse approximation properties

Checked at fixed parameters, at sizes where the exact model is still affordable (n up to 4000), so the exact log likelihood is computed by every framework that supports `ftc`, not only by the oracle:

- **DTCVar is a lower bound.** The collapsed variational bound must not exceed the exact log marginal likelihood at the same parameters (Titsias, 2009). Asserted; a violation fails the build. Note that `size_accuracy__dtcvar_1000` already disagrees with the GPy reference in gpflow, gpjax and gpmat (a known, undiagnosed mismatch). The bound check is independent of which framework is right, and may help diagnose it.
- **Nested inducing sets.** With Z₁ ⊂ Z₂ ⊂ Z₃, the DTCVar bound must not decrease. Asserted.
- **FITC is not a bound.** FITC's log likelihood can exceed the exact one (Bauer et al., 2016). The gap is reported, not asserted, as a known behaviour that users choosing FITC should see.
- **Convergence in M.** The gap to exact for DTCVar and FITC as M grows (16 to 512), reported as a curve per framework.

These need no new operation: they compose `log_likelihood` calls on generated wire models.

### 4. Task descriptors

Every generated case, in every benchmark (existing ones included), records an `x-descriptors` block:

```yaml
x-descriptors:
  n: 1000
  input_dim: 8
  signal_to_noise: 10.0             # kernel variance / noise variance, at the generating parameters
  lengthscale_over_spacing: 3.2     # lengthscale / median nearest-neighbour distance
  log10_condition: 6.1              # of K + noise I, computed when n <= 4000, otherwise null
  generator: {benchmark: timing_exact, case: n1000_d8_rbf, seed: [10, 3]}
```

These are computed by one function in `scripts/benchmarks.py`, so the task-suite CIP can reuse the same code for real tasks and the CIP-0004 guide sees one set of meta-features.

### 5. Additions to the accuracy benchmarks

- **`conditioning`: duplicated inputs.** Exact duplicate rows in X, which make the noise-free kernel matrix singular. Common in real data and handled differently by jitter schemes.
- **`size_accuracy`: higher-dimensional ARD.** d = 10 with ARD lengthscales spanning two orders of magnitude, at n = 500. High-dimensional ARD is a common configuration, and none of the current cases has d > 2.

### Report

A timing section with one table per benchmark: rows are cases, columns are frameworks, cells are warm median (ratio to fastest) with cold time in the tooltip, at one thread and at all threads. A gradient section in the style of the existing accuracy section. A sparse properties section with the asserted checks as pass or fail, and the M-convergence curves as a small figure per framework.

### Out of scope

- Training of any kind (the training sub-CIP of CIP-0004).
- Real datasets (the task-suite sub-CIP).
- GPU timing (an open question in CIP-0004).
- Storing timing history beyond CI artifacts (the results-store sub-CIP).

## Implementation Plan

1. **Descriptors.** Add the descriptor function and write `x-descriptors` into the existing three accuracy benchmarks' generated cases. No behaviour change otherwise.
2. **Timing.** Deliver this through the existing backlog task `timing-benchmarks`, not a second task: its acceptance criteria gain the three benchmark files above, the `grid` expansion with `pr` and `scheduled` tiers, cold time and the thread rule. Close that task when done. If CIP-0005 is not accepted, the task falls back to the single scaling benchmark described in CIP-0003.
3. **Contract version 2 and gradients.** Add `operations` to the task schema, `gradient` to each Python adapter (analytic or by autodiff, converted to wire units) and to the Octave runners (GPML returns derivatives with respect to log hyperparameters; GPmat with respect to its transformed parameters), the oracle cross-check, and the `gradient_agreement` benchmark.
4. **Sparse properties.** The asserted checks and the reported curves.
5. **Accuracy additions.** The two new cases.
6. **Scheduled job.** A weekly workflow running the `scheduled` tier, uploading results as artifacts.

## Backward Compatibility

Additive. Task and result files at version 1 remain valid. The existing benchmark files gain `x-descriptors` in their generated output only; the YAML definitions are unchanged apart from the two added cases.

## Testing Strategy

- Timing repeatability: run twice, compare medians, report the spread; nothing asserted on time.
- A deliberately wrong gradient conversion (for example, dropping the chain rule factor for a log-parametrised hyperparameter) in a test adapter must fail `gradient_agreement`.
- A deliberately broken DTCVar (for example, dropping the trace term) must fail the lower-bound check.
- The descriptor function is checked against hand-computed values on a five-point example.

## Open Questions

- Should the one-thread and all-threads runs both be on every PR, or only the one-thread run (cheaper, more repeatable) with all-threads on the schedule?
- Is 8000 the right ceiling for exact timing on shared CI runners, or should the scheduled tier use a dedicated machine for anything above 4000?
- Should `predict` timing include predictive variances (more expensive, and what users need), or time mean-only prediction as well?
- For gradients with respect to inducing inputs, should a framework that fixes them be reported as refused or as not applicable?
