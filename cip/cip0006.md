# CIP-0006: GP-LVM tier: latent variable models in the comparison

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted
- [x] In Progress
- [ ] Implemented
- [ ] Closed

## Summary

Add a separate tier for Gaussian process latent variable models (GP-LVM): the point-estimate GP-LVM, the Bayesian GP-LVM (collapsed, Titsias and Lawrence 2010; uncollapsed, sampled \(q(\mathbf X)\)) and the multi-view MRD model. These share the single-layer machinery already in scuderia but differ in three ways that break the assumptions of the existing suite:

1. The inputs are latent. The data block carries only \(\mathbf Y\), and a model carries a variational distribution \(q(\mathbf X)\).
2. The latent space is identifiable only up to rotation, scale and (for ARD) permutation. Latent coordinates cannot be compared across frameworks.
3. Training is non-convex with strong dependence on initialisation. Trained results from different frameworks are comparable only through invariant quantities.

The tier therefore starts, as CIP-0005 did, with checks at fixed parameters, and compares trained models only through quantities that are invariant to the latent gauge.

## Motivation

- GPc (`CBayesGplvm`, `CMrd`, and the uncollapsed model of GPc CIP-0030), GPy (`BayesianGPLVM`, `MRD`, `SSGPLVM`, `BCGPLVM`) and GPmat (`vargplvm`) all implement these models. PyDeepGP builds its MRD model on GPy. GPflow and GPyTorch each ship a Bayesian GP-LVM, which I believe but have not verified against the pinned versions in `ci/`. GPJax has none. A user choosing a package for dimensionality reduction currently has no comparison.
- The existing suite cannot host these models without distortion. `data.x` is required by the schema, and the benchmarks compare predictions at test inputs. Neither makes sense when \(\mathbf X\) is a parameter.
- The models are close to what scuderia already checks. With \(q(\mathbf X)\) collapsed to a point mass, the Bayesian GP-LVM bound without its KL term is the collapsed sparse bound (`dtcvar`) with inputs \(\boldsymbol\mu\). That identity connects the new tier to benchmarks that exist, which is the strongest oracle available without an external reference.

## Detailed Description

### Admission rule

CIP-0005's rule applies unchanged, with one addition: **a GP-LVM benchmark must be invariant to the latent gauge.** A benchmark that reads latent coordinates directly is not admitted. Comparisons use bound values at fixed parameters, quantities computed in data space, or subspace distances.

### Wire format

Two new types, `models.gplvm` (point estimate) and `models.bayesian_gplvm` (collapsed bound, diagonal \(q(\mathbf X)\)). The document stays flat, like every other model, with a `latent` block in place of `data.X`:

```yaml
schema_version: "0.1"
type: models.bayesian_gplvm
approximation: dtcvar
inducing_inputs: [[0.0, 0.0], [1.0, 0.5]]          # in latent space, m x dim
kernel: {type: kern.rbf, variance: 1.0, lengthscale: [1.0, 2.0], ARD: true}
likelihood: {type: likelihoods.gaussian, variance: 0.05}
latent:
  dim: 2
  mean: [[...]]        # n x dim
  variance: [[...]]    # n x dim, strictly positive: diagonal of cov q(x_n)
  prior: {type: standard_normal}
data:
  Y: [[...]]           # n x d; no X
```

Rules (schema unless marked):

- A latent model has a `latent` block and `data.Y` only. `data.X`, `input_dim` and `inference` are rejected. Every other model type rejects `latent` and still requires `data.X` and `data.Y`. The likelihood is Gaussian.
- `models.bayesian_gplvm` requires `approximation: dtcvar`, `inducing_inputs`, `latent.variance` and `latent.prior`. `models.gplvm` requires `approximation: ftc` and forbids `latent.variance`, `latent.prior` and `inducing_inputs`.
- `latent.variance` is strictly positive.
- Cross-field rules, checked in `scripts/validate.py` because JSON Schema cannot state them: `latent.mean` has `dim` columns and as many rows as `data.Y`; `latent.variance` has the shape of `latent.mean`; `inducing_inputs` has `dim` columns.
- MRD is `models.mrd` with a list of `views`, each with its own kernel, likelihood and `Y`, sharing one `latent` block. It is added after the single-view model has two framework round trips.

Per CIP-0003 practice, new tags enter `registry/types.yaml` under a reserved section and move into `types` only after a round trip exists. Frameworks without an equivalent record an explicit `null`.

### Benchmarks, fixed parameters first

All run through the runner contract. The runner gains one operation, `bound`, returning the objective at the parameters supplied. For GP-LVM models this is the collapsed bound with the KL term reported separately, so that `bound` and `bound_without_kl` can be compared.

1. **`gplvm_bound_agreement`.** Evaluate `bound_without_kl` and `kl` at a fixed \(q(\mathbf X)\), \(\mathbf Z\), kernel and noise, for RBF, RBF-ARD and linear kernels. These are the kernels with closed-form psi statistics in GPc. Frameworks that use different kernels or only numerical psi statistics record the difference in the descriptor.
2. **`gplvm_collapse_to_sparse`.** Set \(\mathbf S\to 0\) in the shared \(q(\mathbf X)\) and check that `bound_without_kl` equals the existing `dtcvar` log likelihood at inputs \(\boldsymbol\mu\). Tolerance follows `size_accuracy`. This benchmark exercises the psi statistics through their limit, and needs no external oracle.
3. **`psi_statistics`.** Check \(\psi_0\), \(\psi_1\) and \(\psi_2\) against a high-order Gauss-Hermite reference at low latent dimension (\(q\le 3\)), where quadrature is exact enough to serve as an oracle. Frameworks expose these through an optional `psi` operation. Frameworks that cannot are skipped and reported as skipped.
4. **`gplvm_gradient_agreement`.** The CIP-0005 gradient benchmark extended to the gradients with respect to \(\boldsymbol\mu\), \(\mathbf S\) and \(\mathbf Z\), in wire units (variance, not log variance; no transform leakage).
5. **`gplvm_timing`.** Bound evaluation time (gradient timing deferred) against \(n\), \(m\) and \(q\), measured under the CIP-0003 rules. Scheduled tier only.

### Trained comparison, invariant quantities only

Deferred to the sub-CIP that adds training to the runner (CIP-0004 step 2). The agreed measurements are:

- **Held-out reconstruction.** Mask a random subset of output dimensions of held-out points, infer \(q(\mathbf x_*)\) from the rest, and report the test log likelihood and RMSE of the masked dimensions. This is invariant to the latent gauge.
- **Subspace recovery on synthetic data.** Generate \(\mathbf Y\) from a known latent subspace and report the largest principal angle between the learned and true subspaces, using the ARD-weighted latent basis.
- **ARD sparsity.** The number of latent dimensions with relevance above a stated fraction of the maximum, against the number used to generate the data.
- **Bound after training**, reported but flagged as non-comparable across frameworks unless the framework's bound is shown to be the same quantity by benchmark 1.

Initialisation is a confound. Every trained case runs from a common initialisation, PCA of \(\mathbf Y\) for \(\boldsymbol\mu\) and a shared \(\mathbf Z\) subset, and reports the spread over seeds as well as the median.

### What is not claimed

- The uncollapsed (sampled \(q(\mathbf X)\)) model has a stochastic objective. It is compared only through the deep-tier rules of CIP-0008 (estimates within Monte Carlo error), not through exact bound agreement.
- Latent coordinates are never compared directly, and no benchmark scores a framework on which rotation it finds.

## Implementation Plan

1. Extend the schema and registry with `latent` and the reserved `models.bayesian_gplvm` and `models.gplvm` tags; add negative fixtures for each rule.
2. Add the `bound` and `psi` operations to the runner contract. Implement them in the GPc and GPy adapters first, since both have closed-form psi statistics.
3. Add golden `examples/latent/bgplvm_rbf_ard.yaml` with `bound_without_kl`, `kl` and psi values from GPy as the oracle. It lives in a subdirectory because its reference is a bound and psi statistics rather than a prediction, so the prediction-based tools (`compare.py`, the framework snapshot) do not iterate over it. Done: the golden is checked by `scripts/check_latent_ops.py`.
4. Add the benchmarks in the order 1, 2, 4, 3, 5. Benchmark 2 comes early because it needs no new oracle.
5. Add GPmat (through the Octave route already used by the GPML adapter), then GPflow and GPyTorch once their model classes are confirmed against the pinned versions.
6. Write the trained-comparison sub-CIP.

## Backward Compatibility

Additive. Existing documents and benchmarks are unaffected. The schema accepts `latent` only with the new model types. Frameworks that do not support GP-LVM models refuse them with `UnsupportedByFramework`, as CIP-0001 already specifies for unsupported features.

## Testing Strategy

- Schema: valid and invalid fixtures for `latent`, including `data.x` present, non-positive `variance`, and dimension mismatches.
- Cross-framework: benchmarks 1 and 2 are the conformance gates. A framework that fails benchmark 2 has a psi statistic or bound that disagrees with the sparse GP in the limit where the two must agree.
- Gradients: finite-difference check per framework, as in CIP-0005.
