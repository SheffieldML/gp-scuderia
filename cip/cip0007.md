# CIP-0007: R frameworks: kergp, DiceKriging and GauPro

## Status

- [x] Proposed - Initial idea documented
- [x] Accepted
- [ ] In Progress
- [ ] Implemented
- [ ] Closed

## Summary

Add a first R runner kind to gp-scuderia and use it to bring in three R packages as frameworks: `kergp` and `DiceKriging` in phase one, `GauPro` in phase two. All three are exact-GP packages. They test the Gaussian-likelihood, exact-inference slice of the wire format against implementations that share no code, authors or conventions with the Python, Octave and C++ frameworks already covered.

Other R packages (`laGP`, `GpGp`, `gplite`) use approximations that the wire format cannot yet name. We record them as candidates and defer them until the approximation vocabulary can express them.

## Motivation

- **R is where much of the applied GP community works.** Kriging and computer-experiment users in particular use `DiceKriging` and `kergp`. A shared interchange format that cannot reach R leaves that community outside the comparison.
- **Independent implementations make conformance stronger.** The seven current frameworks share lineage: GPy, GPc and GPmat come from one group, and GPflow, GPyTorch and GPJax follow similar conventions. R packages were developed separately, with different parameterisations and different defaults. Agreement with them is better evidence that the wire format is not secretly GPy-shaped.
- **The machinery is ready.** CIP-0003 made a framework a YAML file plus a runner that speaks JSON. R needs a new runner kind and an adapter, and no change to the harness.
- **CIP-0004 needs rows.** Its results matrix is more useful if the exact-GP family (A1) spans more than the Python stack.

This follows the interoperability tenet: speak the formats the community already uses, and do not require a new framework to change the harness.

## Detailed Description

### Candidate survey

The survey below is from the packages' documentation as we remember it. We have not installed them for this CIP. Phase 0 (below) exists to verify every claim before anything is committed to a framework file.

| Package | Model | Kernels | Fit | Decision |
|---|---|---|---|---|
| `kergp` | Exact GP, Gaussian noise, kernel composition | Sums and products of stationary kernels, ARD, user-defined kernels | Maximum likelihood with gradients | Phase one. Closest to GPy's composition model. |
| `DiceKriging` | Exact GP (kriging) with a linear trend and optional nugget | Gaussian, Matérn 3/2 and 5/2, exponential, power-exponential; separable ARD | Maximum likelihood | Phase one. Widely used, narrow model, good independent check. |
| `GauPro` | Exact GP, R6 classes | Gaussian, Matérn, sums and products of kernels | Maximum likelihood with gradients | Phase two. Cheap third implementation. |
| `laGP` | Local approximate GP | Isotropic and separable Gaussian | Local fitting | Deferred. Local approximation has no wire tag. |
| `GpGp` | Vecchia approximation | Matérn family | Maximum likelihood | Deferred. Vecchia has no wire tag. |
| `gplite` | Low-rank basis-function approximation, non-Gaussian likelihoods | Squared exponential, Matérn | Maximum a posteriori | Deferred. Needs a basis-function approximation tag and non-Gaussian goldens. |
| `GPfit`, `mlegp`, `tgp`, `RobustGaSP` | Narrow or different model classes | | | Excluded. They add little beyond `DiceKriging`, or capture parameter estimation rather than the model. |
| `brms` `gp()`, `INLA`, `spBayes` | Bayesian or SPDE representations | | | Excluded. They do not map to a point-estimate parameter tree. |

Wrappers that call a Python framework from R (for example through `reticulate`) are excluded, because they would re-test frameworks already covered.

### What the wire format can express for these packages

Expected capabilities, subject to phase 0:

```yaml
# frameworks/kergp.yaml (expected)
capabilities:
  approximations: [ftc]
  kernels: [rbf, matern32, matern52, white, add, prod]   # ARD to be confirmed
  likelihoods: [gaussian]
  inference: [exact]
  extras: []                                              # no wire mean or normalizer assumed

# frameworks/dicekriging.yaml (expected)
capabilities:
  approximations: [ftc]
  kernels:
    - rbf: {options: [ard]}
    - matern32: {options: [ard]}
    - matern52: {options: [ard]}
  likelihoods: [gaussian]
  inference: [exact]
  extras: [mean.constant]    # constant trend only; linear trends have no wire tag yet
```

Declared capabilities decide which goldens each runner must match and which it must refuse. Where a package cannot express a wire model, the adapter refuses with a reason and never substitutes.

### Parameterisation hazards

Each of these has to be settled in phase 0 and written into `docs/`, because a mismatch here produces silent wrong answers, not errors.

- **Lengthscale convention.** Packages differ on whether the parameter multiplies or divides the distance, and on whether the squared-exponential carries a factor of 2 in the exponent. The wire format fixes one convention, and each adapter converts.
- **Variance and noise.** `DiceKriging` separates a process variance (`sd2`) from a nugget, and its nugget may be specified as a variance or a ratio. Check whether the likelihood treats the nugget as added noise or as part of the kernel diagonal.
- **Fixed Matérn smoothness.** `DiceKriging` supports only particular smoothness values. A wire `matern*` type outside that set is refused.
- **Trend.** A `DiceKriging` model with a linear trend is a GP with a linear mean fitted by generalised least squares. The wire format has `mean.constant` only. Linear trends are refused until a mean tag exists (see the `mean-and-normalizer` backlog task), and are never approximated by a constant.
- **Likelihood and prediction conventions.** Log likelihood can be reported with or without the trend profiled out, and predictive variance may include or exclude the noise term. The adapter must report the quantity the wire runner contract defines, not the package default.
- **Jitter.** Packages add small diagonal terms by default. The small-noise gap found in CIP-0005 (GPy's 1e-8 term) is a warning that this affects agreement at low noise. Each adapter records its jitter, and the conformance report states it.

### R runner kind

Add `kind: r` to the runner contract in CIP-0003:

```yaml
name: kergp
runners:
  - id: r
    kind: r
    script: R/kergp/runKergp.R
    install: {pinned: ci/pinned-r.txt, latest: ci/latest-r.txt}
    versions_from_run: true
```

- The script reads the JSON task file and writes the JSON result file, with the same `{log_likelihood, mean, var}`, `{refused}` and `{error}` shapes as every other runner.
- A thin shared helper (`R/gpscuderia/`, mirroring `octave/gpscuderia/`) reads a wire document, builds the native model, and maps parameters to and from the wire convention. Package-specific code lives under `R/<package>/`.
- Packages are installed by pinned versions from CRAN (a snapshot date or an `renv` lockfile), with a `latest` mode as for Python. The CI job installs R through the standard `r-lib/actions/setup-r` action.
- JSON and YAML handling uses `jsonlite` and `yaml` on the R side. Both are CRAN packages with no system dependencies.
- Timing is measured inside the runner after warmup, as in CIP-0003, so R start-up and package loading are excluded.

### Relation to the oracle and to CIP-0004

The oracle remains GPy. R frameworks are checked against it in the same way as the others. In CIP-0004's matrix, R packages supply rows only for family A1 (exact regression), and phase two of this CIP does not add rows for any other family. Because these are fitted by their own optimisers, the training protocol of CIP-0004 applies when it exists. Until then, conformance and benchmarks at fixed parameters are the scope here.

### Out of scope

- Approximations other than FTC. `laGP`, `GpGp` and `gplite` are deferred until the approximation vocabulary of `docs/` can name them, and each would be a separate CIP.
- Non-Gaussian likelihoods in R.
- Training or optimiser comparisons (CIP-0004).
- Calling gp-scuderia from R as a user-facing library. Reading and writing the wire format from R is a by-product of the adapters, and may later be packaged.

## Implementation Plan

### Phase 0: probe

Install the three packages and check, for each wire kernel and each golden, what the package can and cannot express, in the manner of `2026-11-27_gpml-probe`. Record parameterisations, likelihood conventions, jitter and defaults. The output is a probe note and corrected capability lists. Close or amend this CIP's expectations if the probe contradicts any claim above.

### Phase 1: runner kind and `kergp`, `DiceKriging`

1. Add `kind: r` to the runner contract, with a stub R runner exercised by `scripts/check_runner_contract.py`.
2. Add `R/gpscuderia/` (read, write, convention conversion) and the first adapter.
3. Add the framework files and pinned and latest install lists.
4. Add the R job to the generated CI matrix.
5. Document parameter conversions in `docs/`.
6. Run goldens and the accuracy and gradient benchmarks that the declared capabilities allow.

### Phase 2: `GauPro`

Add the third adapter once phase 1 is stable, reusing the shared R helper.

## Backward Compatibility

Additive. Existing frameworks, goldens and the runner contract for `python`, `octave` and `command` are unchanged. The registry gains entries for the new frameworks, with explicit `null` for unsupported types, as before. The CI matrix gains an R job. No wire schema change is needed for phase one.

## Testing Strategy

- **Conformance.** Every golden matches within tolerance if declared as supported, and is refused with a reason otherwise. The harness checks both directions, as in CIP-0003.
- **Cross-check.** Agreement with the GPy oracle on log likelihood and predictions at fixed parameters, at several noise levels including the small-noise regime that exposed the jitter gap in CIP-0005.
- **Gradients.** Where a package exposes likelihood gradients (`kergp` and `GauPro` do, we expect), compare them with the oracle through the existing gradient benchmark. Where it does not, say so in the framework file and skip, and do not finite-difference through a black box and call it a package result.
- **Refusals.** Linear trends, unsupported smoothness values and non-Gaussian likelihoods must be refused, with tests that fail if an adapter substitutes.
- **Runner contract.** The stub R runner passes the same contract check as the stub Python and Octave runners.
